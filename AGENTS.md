## Repository-wide rules

- Never use em dashes anywhere in this repository, including code, comments, documentation, tests, commit messages, and generated content. Use commas, colons, parentheses, or regular hyphens instead.
- Keep this `AGENTS.md` current. Update the relevant instructions whenever repository structure, commands, conventions, or workflows change.
- Write every commit as a Conventional Commit (`type(scope): subject`), with a scope whenever the change has an obvious one (`player`, `electron`, `explore`, `settings`, and so on) and none when it spans the repository. Add a body whenever the subject line cannot carry the reasoning on its own: what was wrong, why this change, what it costs.
- `README.md` and `CONTRIBUTING.md` are the outward-facing pair and restate nothing this file explains: the README says what the app is, why it exists and how to run it, and `CONTRIBUTING.md` points here for the reasoning behind any rule it states. A convention changed here has to be changed there too, since a contributor reads that file and never this one. The README's screenshots live in `docs/screenshots/` at 1440x900, and `docs/banner.png` is a 2400x600 render with no generator committed: it was drawn from a throwaway HTML file, so a new one is drawn again rather than regenerated.
- `.github/workflows/ci.yml` runs `pnpm check` on every pull request and every push to `main`, and it is the only gate on a contribution, since nothing is enforced by a git hook. It runs on `ubuntu-latest` rather than the `macos-15` the release uses, which holds only while no test touches `process.platform`, the Keychain or `mdfind`: `scripts/dev-app-name.mjs` is already a no-op off macOS, and a test that stops being portable moves the runner rather than being skipped.

## Noctune architecture

- Node 26 and pnpm 11.16.0 are required. The Node line is pinned by major only (`engines`, `.node-version`, the release workflow all read `26`), since a patch pin buys nothing here and goes stale every fortnight. Dependency ranges are still not allowed.
- `electron/` contains the privileged main process, sandboxed preload bridge, YouTube adapter, secure protocols, state, and lyrics.
- `src/shared/` contains serializable contracts and pure logic shared across process boundaries. Entity narrowing lives in `src/shared/entities.ts`, not in components.
- `src/routes/` uses TanStack Router file routes with hash history. Run the matching TanStack Intent command before route or router edits. Data loading is TanStack Router loaders only, there is no query client.
- `src/components/ui/` is generated shadcn/Base UI source. Use the shadcn CLI and current component docs before modifying it. `sidebar` and `sheet` were removed on purpose: the navigation rail is a plain element in `app-shell.tsx`.
- `src/lib/audio-engine.ts` owns playback state, the two audio decks, the WebAudio gain graph, and persistence. It is framework-free and unit tested. `src/player.tsx` is only a React binding over it: `usePlayer()` for actions, `usePlayback()` for state, `usePlaybackPosition()` for the separate high-frequency position channel. The stored volume is the slider's position, never a gain: the bus reads it through `volumeGain`, which spends 10 dB on every halving, since a position written straight onto the gain leaves the top half of the travel sounding like nothing changed. Normalization moves a track to the target from either side of it: attenuation is uncapped, while the lift is capped at `maxBoostDb` (6 dB), because YouTube publishes an integrated loudness and no true peak, so a quiet, dynamic master may already be peaking near full scale and a lift sized off the loudness alone clips it. 6 dB is the range that occurs, carrying a -19 LUFS master to -14 exactly. `assumedIntegratedLufs` stays -9 and is load-bearing twice over: it sits above every target, so an unmeasured stream can only ever be attenuated, never boosted into the loud failure it exists to prevent.
- The renderer publishes every media `timeupdate` to the in-memory `StateStore`, while ordinary interval and close saves remain the only disk writes. This keeps resume precision at the media event cadence without writing the state file four times a second. Space is captured in preload before React mounts, queued until `PlayerProvider` restores playback, and treats `loading` as optimistic playing state so a second press cancels an in-flight start immediately. It is the transport control and nothing else: outside a text field the handler both prevents the default and stops propagation, since it runs in the capture phase on `window` and is therefore the only thing that can keep the key away from whatever holds focus. A menu trigger left focused by a menu that has just closed reopened it on Space instead of pausing, and every button, menu item and select in the app would do the same; a range input is exempted from the typing test for the same reason, since a slider's thumb takes focus on click and types nothing. Startup prepares the restored track without playing it, which keeps the first Space press off the resolver fast path when preparation finishes in time. A start that does not reach playback in 15 seconds invalidates its generation and clears the active source, which aborts the stuck request and makes the next attempt resolve a fresh stream instead of reusing it.
- `useSystemIntegration` in `src/player.tsx` is the whole of the macOS Now Playing widget: Chromium turns the `MediaSession` metadata into what Control Center draws. The cover cannot be the `noctune:` URL the app itself renders, since Chromium downloads Now Playing artwork itself rather than reusing the page's copy and does not resolve the scheme, so the renderer fetches it and hands the widget a data URL. Its size is measured off the decoded image rather than claimed, because an entry stating none scores as sizeless and can lose the selection to nothing at all. The text is written first and the cover replaces it when the fetch lands, so the widget names the track on the tick playback starts and a failed fetch costs the artwork alone. The whole write is also replayed when the status reaches `playing`, not only when the track changes: Chromium builds the Now Playing entry when a deck actually starts, and a write that landed before that moment is not what it reads, so the widget names the application ("Electron") instead of the song. `currentTrack` is set while the track is still resolving, and a resume or a restored session never changes it at all, which is why the track alone is not enough of a signal. The last cover is held in `lastArtwork` so the replay costs no second fetch.
- The Now Playing widget names what is playing, and the notification names what changed, which is why only the queue's own moves reach it. `move` takes an `auto` flag set by its two callers nobody pressed, the armed handoff and the deck's `ended`, and `play` reads it on the same tick and sends `player.notify` at the point it reports the start, so a track that never resolved announces nothing and a press announces nothing either. Repeat "one" advances onto the track already playing and is skipped for that reason. Main draws it (`notifyTrackChange` in `electron/main.ts`) rather than the renderer, since a web `Notification` needs a permission the window's handler refuses, and since the setting is in the store main already holds. Nothing is shown while the window has focus, the banner is `silent: true` because the one sound this app makes is the music, and the cover goes through `handleArtwork` rather than beside it, so the host check stays in one place. macOS draws that image as the notification's content image, which is the thumbnail on its trailing edge. Whether the system will draw it at all cannot be asked in advance: Electron exposes no authorization status, and a permission that has merely never been asked for is granted by the first `show()` rather than refused by it, so the only honest signal is the `failed` event. `notificationsRefused` holds it, the `show` event clears it (permission is granted in System Settings while the app runs and nothing tells us), and `/settings` reads it through `player.notifyRefused` on mount, so a switch that is on and silent says why. It is read rather than pushed because nothing is ever drawn while Noctune has focus, which is the only time that page is open.
- Gapless is the whole reason there are two decks, and it needs both halves of the engine to agree on what plays next. `preloadNext` prepares the track `nextQueueIndex` will actually pick, not `queueIndex + 1`: repeat "one" replays the current track, repeat "all" wraps off the end, and shuffle jumps, so preparing the row after this one made all three miss the fast path and resolve a stream at the boundary, which is seconds of silence rather than a gap. `move("next")` then honours the index the preload settled on rather than computing its own, since with shuffle on a second roll of the die lands somewhere else and throws the prepared deck away. The switch itself is armed ahead of the boundary and never driven off `ended`, which only fires once the deck has already drained: `armHandoff` reads the remaining time off a `timeupdate` and schedules `move("next")` for `SWITCH_LEAD_MS` before the end, `play` leaves the outgoing deck running so its tail plays out under the new track instead of being cut, and `play`, `pause`, `seek` and `clearDeck` all clear the armed timer, which is also what stops a late one from advancing twice when `ended` beat it there. The lead is one fixed number covering Chromium's element start latency and the `local.load()` round trip, so it is the knob to turn if a join ever sounds doubled or gapped. `backgroundThrottling: false` on the window belongs to this: a hidden page's timers are throttled to one a second, and a minimised window is the normal state for a music player.
- Autoplay (`Settings.autoplay`, on unless exactly `false`) hangs off that same preload, not off the boundary. `extendQueue` grows a queue that has run out with the radio upstream builds around its own **last** row, and it is fired from `preloadNext`'s `shouldStop` branch, a whole track early: a radio fetched once the deck has drained is silence for as long as the round trip takes, while one fetched now leaves time to preload its first row and hand off gaplessly. Re-entering `preloadNext` afterwards cannot loop, since the appended rows are exactly what stops `nextQueueIndex` reporting `shouldStop` again. `move`'s own `shouldStop` branch is the race path only: it pauses, which is the honest state once a deck has drained with nothing to move to, then awaits the promise the preload already started rather than calling `extendQueue` itself, since two calls for one seed are two different hundred-song orders. The seed is the queue's last track and not the one playing, because those differ exactly when it matters. The whole page goes in rather than a slice, which is what upstream's own queue does and what `extractQueueTracks` already caps, and rows already in the queue are dropped, since a radio seeded off the last track tends to open on it. `playback.context` is left alone: an album that autoplays on still reads as playing from that album, and the rail badges that row with the same `PlayingBars` a track list uses, keyed on `playback.context.id` rather than on any track id, since the same song sits in several playlists.
- Playback depends on two upstream workarounds that look like dead code. `YouTubeAdapter.resolve` walks `YTMUSIC`, `TV_SIMPLY`, then `IOS` because the WEB and ANDROID clients return SABR-only formats with no URL to decipher while `TV` and `MWEB` return a URL that googlevideo answers 403 for without a proof-of-origin token, and the decks set `crossOrigin = "anonymous"` against the `access-control-allow-origin` that `handleMedia` echoes, because `createMediaElementSource` outputs silence for a tainted element and development serves the renderer from Vite's origin. Removing either one brings back a silent failure. `handleMedia` must also preserve a non-success upstream status even when the deck requested a range: presenting its error body as `206 Partial Content` makes Chromium retry it instead of failing the element.
- Downloads reuse that same resolver and stay in main. `local.download` stores each validated track under Electron's `userData/downloads`, while `PersistedState.downloads` keeps its serializable metadata and exact audio fingerprint. `/library` reads those records for its Downloads tab, where the menu calls `local.removeDownload` to remove both the file and its metadata. `player:resolve` prefers the local file before asking YouTube, so playback works offline without exposing a signed googlevideo URL or filesystem path to the sandbox. `SecureResourceRegistry` serves the file with byte-range support through the existing `noctune:` media protocol.
- Anything upstream that only feeds `extractEntities` goes through a raw `/browse` with `parse: true`, not a `client.music.*` wrapper. Those wrappers assert a node layout YouTube keeps changing (`getLibrary` throws on today's response), and the duck-typed walk does not care. That parse returns the tree inside a `SuperParsedResult`, which holds it in a private field, so `#browse` unwraps it (`is_array ? array() : item()`) and hands `walk` the contents themselves. Passing the response instead does not make a shorter page, it makes an empty one: explore and the library both returned nothing at all until it was unwrapped.
- Home is the exception to flat page rendering: `YouTubeAdapter` preserves each shelf as a `Page.sections` entry, including its title, strapline, header artwork, item order, `num_items_per_column`, its `layout`, and its own More target. Deduplication is per shelf, not across shelves, because the same recommendation can intentionally appear in more than one upstream group. Keep `Page.items` as the flat compatibility fallback, and do not flatten Home again. Home reads its shelves through `mediaSection`, the same one Explore uses, over the same `shelfTypes` list: a shelf is whatever container upstream drew it in, so nothing keys on `MusicCarouselShelf` alone or on a `sections` field. The six tiles the lead shelf is promoted into (`QuickTile`) follow the same split every card and row in the app follows: the tile opens what it names, a song through `TrackLink` to the release it came from, and only the play button over the artwork starts anything. That shelf mixes songs, albums and playlists, so a tile that played on click while the one beside it navigated was two controls wearing one shape, and the line under the title leads with `entityKind` for the same reason a mixed row does: nothing else on a tile says whether it is a song, an album or a single.
- `music.getHomeFeed()` is not used and must not come back. It asserts its shelf list down to `MusicCarouselShelf` and `MusicTastebuilderShelf`, so one unrecognised shelf throws the whole feed away, and its `getContinuation` rebuilds a `HomeFeed` from a response that has no browse tab in it, which means a second page never worked through it. `#home` sends the raw `/browse` the wrapper sent anyway, so the first page, a chip-filtered page and a continuation page are one path through one walk. A continuation response carries no `contents`, only `continuation_contents`, which is why `#continue` exists beside `#browse` rather than inside it.
- Home's chips and its next page are opaque tokens minted in `#homeTokens`, never the upstream parameters themselves, which is what keeps `/`'s search param free of them. Unlike `#continuations` these are never spent: a chip has to survive being tabbed away from and back to, and a continuation has to survive the router serving a cached first page whose token was already used, which would otherwise strand a reader at the bottom of a feed that can no longer grow. The map is capped rather than expiring, and an evicted chip degrades to the unfiltered feed while an evicted continuation ends the scroll. Answering an unknown continuation with the first page instead would append what is already on screen, forever. `extractHomeFilters` drops the podcasts chip, since Noctune does not play them and the chip filters the feed down to rows that do nothing: it is matched on the label, the "podcast" loanword in most locales, because a chip's params are an opaque protobuf and every chip shares one browse id. The feed itself is bled out of the shell's padding (`-mx-6 px-6`) so the artwork wash behind it reaches both window edges.
- The renderer grows the feed with an IntersectionObserver against `#main-scrollable-area`, not the viewport, which also holds the top bar and the player bar and so measures a margin from the wrong edges. `homeShelves` and `appendPage` in `src/shared/entities.ts` are the pure half and are where the two non-obvious rules live: only a first page may fall back to the four kind shelves, since a later page synthesising its own would file a second "Quick picks" under the first on every scroll, and a page whose key no longer matches is dropped rather than appended, which is what a chip tapped mid-fetch produces. `/` takes no params, so a chip change never remounts it: the grown state is derived against the current chip, never reset in an effect.
- Explore is the other structured-page exception. `YouTubeAdapter` keeps its shortcut Grid and each navigation or media container in `Page.explore`, promotes the landing mood section without reordering the remaining shelves, names the page in `ExploreData.title` when the response names it, and leaves `Page.items` as the root fallback. That name is read off the browse response's own `header`, which is why `#browse` unwraps and hands back both halves: a destination states it there and nowhere in the shelves below, so titling the page off its contents named every one of them after its first shelf ("Songs" over a shelf of songs, and no genre named anywhere). The renderer falls back to the lead section's title, and then leaves that section unheaded rather than printing the same words twice, which is also what keeps the Charts page from stating "Charts" over a shelf upstream calls "Charts". The renderer promotes nothing of its own: doing it in both places was the same reorder run twice. Destination browsing stays on `/explore` through validated `browseId` and opaque `params` search values, except playlist More targets, which use `/playlist/$id`. A media card also carries a browse endpoint, so only `MusicNavigationButton` items are navigation: treating every browse endpoint as navigation turns album shelves into image-free links back to Explore. Preserve Grid, `MusicCarouselShelf`, `MusicShelf`, and `MusicPlaylistShelf` boundaries, repeated items across shelves, More endpoints, and ranked responsive rows. Video entities are filtered before either structured shelves or the flat fallback reaches the renderer, which also removes video-only shelves of cards such as "New music videos". A shelf of ranked rows is the exception, and only on Explore: a chart row is a song whatever upstream types it, and "Trending" is eighteen clips in twenty rows, so filtering it left two songs under a heading promising a chart. The split is the row shape (`MusicResponsiveListItem` keeps its videos, `MusicTwoRowItem` does not), which is the same thing `layout` already reads, and Home keeps filtering both. The shortcut tiles pick their icon by browse id (`FEmusic_new_releases`, `FEmusic_charts`, `FEmusic_moods_and_genres`, a compass for anything else), never by position in the Grid, which upstream reorders and adds to. A tile the promoted mood section adopts as its "Browse all" is removed from that Grid, since the tile and the section header led to the same browse a heading apart: the shortcuts are the destinations not already on the page, and the same label match decides both, so a response whose wording no longer lines up keeps them as they arrived. The Grid is `auto-fit` rather than three columns for that reason, and its pending state draws the two tiles the landing normally resolves to.
- The landing is rails, a destination is mostly not: a page reached by asking for everything under one heading shows the whole list, so a media section there is a `MediaGrid` and a chart is a full-width `MediaList`, where a rail would hide most of what was just opened. Only the landing's mood section stays a two-row rail. The one destination section that does rail is a list upstream never numbered, which a genre page opens with: fifty rows down the page is the page, and everything else on it starts below the fold. It rails five to a column and is numbered nowhere, since nothing ranked it, and the presence of an upstream rank is exactly what tells the two apart. `MediaShelf` caps its rows at five for that one caller: upstream's own `num_items_per_column` never exceeds four. A chart row states its own place (`Track.rank`, `Artist.rank`) and both `MediaShelf` and `MediaList` prefer it over the row index, since any row dropped on the way here (a kind `extractEntities` has no entity for) would otherwise renumber everything under it, and a row upstream never numbered would be given a place it does not hold. A chart is also per country, and each region is a browse of its own rather than a parameter of this one, so `ExploreData.regions` carries them as targets and the picker on the title row navigates: the option upstream flags is the one the page already answers, and a response flagging none falls back to the first. `/explore` cannot throw, for the same reason `/` cannot: no route below `__root` has an error boundary, so a failed browse would take the whole shell down over one page. The loader answers an empty page instead, and the route's own pending component is shaped like the real one, since the global skeleton is a grid and this page is a title, tiles and rails. Its landing is refreshed on the way out into `heldFeeds.explore` exactly as `/` is, and for the same reason: a feed left standing until the cache drops it resolves the next visit's skeleton into shelves the reader never saw arrive, which is the swap `defaultStaleTime` exists to prevent, only deferred. Only the landing is warmed and only its cached match is dropped, since a destination is a page asked for by name and cached under a browse id of its own.
- A genre tile's colour is hashed from its label, because upstream's own is unreachable: youtubei.js parses a `MusicNavigationButton` down to `button_text` and `endpoint`, so the chip colour is gone before the adapter sees the node. The hash feeds a hue through the golden angle, so neighbours never land on one colour, and only the hue varies: the lightness and the chroma come from the class, one pair per theme, which is what keeps every tile at the same weight with white text legible on all of them. An artist page carries a shelf of music videos, lyric uploads and live clips beside its top songs, and both `/artist` and `/search` render one flat song list off that page, so those rows would read as duplicates of the songs with no release and no length: they are not in the top songs playlist either, so `withTopSongs` cannot fill them in. Home passes it too, for the same reason: its shelves of live clips, lyric uploads and hour-long uploads read as duplicates of the songs beside them, and a shelf left with nothing else in it is dropped like any other empty shelf. A playlist that holds a video still means to hold it, and keeps it. Podcasts stay: they are results someone searched for. An unfiltered search still rebuilds a top result card that points at a watch endpoint, since the mixed list may not repeat the ranked track. Its linked subtitle runs supply the artist and trailing duration.
- A radio queue is YouTube Music's own ranking and nothing reorders it, but it does need pruning. `music.getUpNext` asserts down to an automix node, so `#queryMusic` calls `/next` raw with `RDAMVM<videoId>` as the playlist (a bare `videoId` answers with one row and a placeholder), and reads the rows out of `contents_memo` because a parsed watch-next keeps its contents in a `Map` the walk cannot descend. Every row upstream has a music video for arrives inside a `PlaylistPanelVideoWrapper`, the song as `primary` and the clip as a `counterpart`, which is the "Switch to video" toggle rather than a second entry, and the memo files both under `PlaylistPanelVideo`. So `extractQueueTracks` names the counterparts in a pass of its own before collecting anything, since the memo lists every video before any of the wrappers. Without it a radio plays each such track twice in a row, the song and then its clip a few seconds longer.
- Lyrics come from three providers, ranked in `src/shared/lyrics.ts` and fetched in `electron/lyrics.ts`. `pickBest` is the single ranking authority and orders by quality before source: synchronized beats an instrumental marking beats plain text, and LRCLIB beats NetEase beats YouTube Music only inside a tier. So a synced NetEase answer wins over a plain LRCLIB one, which is the whole reason there is more than one source. The providers are asked in sequence rather than in parallel, and `isBestPossible` stops the loop on the top tier: since it only short-circuits there, the answer is identical to fetching all three and ranking, and most tracks never get past LRCLIB. Ranking lives in main because main is what needs to know when to stop asking, so `src/lib/lyrics.ts` is a bare fetch.
- Two things about that walk look like overcaution and are not. NetEase stamps its writing and production credits as real LRC lines from `[00:00.000]` in 25ms steps, so `stripCredits` drops a short label before a colon inside the first second; without it those render as the opening lyrics and hold the active line for the first second of playback. And `YouTubeAdapter.lyrics` reads `Text` through the local `text()` rather than `toString()`, which returns the literal string "N/A" for an empty field, which would then rank above a real plain result. `music.getLyrics` is one of the asserting wrappers, and it throws on the ordinary "no lyrics" answer as readily as on a re-layout, so both are caught as one empty tier.
- Those credits are all NetEase holds for a track nobody has transcribed, and it stamps that file `[00:00.00-1]` rather than `[00:00.000]`, so `parseLrc` tolerates the `-1` suffix: a tag it does not parse is a tag left in the text, and the file then ranks as plain lyrics with the brackets still showing. `toResult` falls back to the raw `syncedLyrics` only when nothing timed parsed at all, not when `stripCredits` emptied it, or the same file comes back as its own plain text through the other door.
- A duration filter that compares against a zero would reject every candidate, and half the rows in this app carry no length, so `matchesLength` keeps a candidate when either side states none. Only some sources time their lyrics at all, so the panel renders an untimed result as a static block with no highlight and nowhere to seek, and credits `attribution` when the provider names its own licensor instead of `Lyrics by {source}`. Once opened, `LyricsPane` stays mounted while the panel is closed or showing the queue, so its loaded result and position sync remain warm; it is not mounted before the first lyrics view, which avoids provider requests for a feature the listener never opened.
- A lyrics request carries no cookie (`credentials: "omit"`), and none of these hosts belong in the renderer's CSP `connect-src`: the renderer only ever fetches `noctune://app/lyrics`, and main makes the outbound call. YouTube Music is the one tier tied to the linked account, since it rides the InnerTube session. Adding a source means naming it in `PRIVACY.md` and `THIRD_PARTY_NOTICES.md`, which the `lyrics-rights` release gate covers.
- `src/lib/theme.ts` is the single owner of the `data-theme` attribute. Do not write it anywhere else. It also mirrors the choice into `localStorage` on every write and paints from that mirror at import, ahead of the first render, because the state file it comes from is an IPC round trip away: painted from the OS preference instead, a stored "light" opened the window dark and corrected itself in view, and `/settings` selected the default card and moved the selection a frame later, which is the glitch a reader actually sees. The state file stays the owner and `__root` applies what it loads, which is what repairs a mirror that ever falls behind, and `/settings` seeds only its `theme` from `storedTheme()`, since every other row there has no synchronous source. The window's own opening colour is the last part of it: `createWindow` reads the stored theme and resolves `system` through `nativeTheme.shouldUseDarkColors` to pick the matching `--background`, since nothing in the renderer can paint before the frame Electron shows.
- `__root.tsx` holds the auth state and gates the app: with no linked account it renders `src/components/sign-in.tsx` instead of `AppShell`. There is no demo or offline data, so every view is empty until the bridge answers.
- Playback is refused to an account holding no Music Premium subscription, and `authState` in `electron/main.ts` is the one place that decides it, since every entry passes through there. Noctune plays without advertisements, in the background, out of its own engine, and those are the three things YouTube sells that subscription for: asked of an account that pays for them it hands back what was already bought, and asked of a free one it hands over what YouTube charges for. Nothing upstream states the entitlement, which is why youtubei.js parses none and why the account menu is no use (its "Paid memberships" row means a channel membership or a bought film just as readily). What a subscription does change is what `/player` will offer, so `YouTubeAdapter.entitled` probes it and `readEntitlement` reads the answer: itag 141 and itag 774, both `AUDIO_QUALITY_HIGH`, are offered to a subscriber and to nobody else, where a free account tops out at the ~130 kbps 140 and 251. It is one fixed track (`ENTITLEMENT_PROBE_ID`) and never the one about to play, since the high tier is per master as well as per account and a track nobody mastered above 128 would refuse a paying listener. `undefined` is the third answer and it allows: a failed request or a response with no audio formats is "not asked" rather than "asked and refused", and locking someone out of music they pay for over a dropped connection is the worse failure by a distance. Only `false` refuses, as `AuthState.status: "unentitled"`, which is a status and not an error because the sign-in did not fail: `__root` draws `PremiumRequiredView` for it, and the two import paths throw `UNENTITLED_MESSAGE` and write no link, so a refused profile leaves nothing behind.
- `electron/browser-cookies.ts` is the only way in: it reads the YouTube cookies out of a signed-in browser profile and main writes them into the auth partition. Chromium forks (Chrome, Brave, Edge, Vivaldi, Chromium) are macOS only because their key lives in the Keychain, Firefox works anywhere because it does not encrypt. Do not add an embedded Google sign-in window or an OAuth device flow, both are refused upstream. A renderer only names a profile that was already listed, never build a path from its input. A listed account also states who it belongs to, which is read from the Chromium fork's own `Local State`: plain JSON beside the profiles, holding each profile's display name, its signed-in Google account and the filename of its picture, and needing no Keychain access, so the picker costs no permission prompt. That account is the browser profile's, not necessarily the one owning its YouTube cookies, so no copy may present it as the account Noctune will use. Firefox states none of it. The row's icon is the browser's own application icon, found by bundle id through `mdfind` and rendered with `nativeImage.createThumbnailFromPath`, which is why that lookup sits in `main.ts` and not in `browser-cookies.ts`: that module has a unit test loading it directly, and an `electron` import at module scope would break it. `app.getFileIcon` is what it must not be: it answers every path with the same grey placeholder grid, since it asks IconServices for an icon that is still loading and returns the stand-in rather than waiting, and a call seconds later gets the same one. It is also the one that must never be asked for the `"large"` size, which macOS does not have and which aborts the main process rather than rejecting, with no exception to catch and nothing on stderr. A browser whose application is gone still lists its leftover profile, and correctly shows no icon.
- The copied cookies go stale: Google rotates `__Secure-1PSIDTS` every few minutes and retires the old value, which leaves the session recognised but downgraded, so browsing still answers while every stream URL it mints returns 403. `linked-account.json` in `userData` names the profile the session came from, and `cookieHeader` re-reads that profile at most once a minute; a changed header makes `YouTubeAdapter` build a new InnerTube session, since the old one keeps its cookies from the moment it was built. Nothing renews the copy from inside the app: InnerTube answers carry no refreshed cookie, and neither does routing its requests through the auth partition's own session. That re-read is the whole reason a browser profile is the only way in: a session copied once and never refreshed is a session that browses fine and plays nothing, which is exactly what the pasted Cookie header used to be.
- There was a manual Cookie header import beside the browser picker and it is not coming back. It asked a listener to open developer tools, find a request to `music.youtube.com`, and copy a credential out of it by hand, which is both the hardest thing the app ever asked for and a shape worth teaching nobody, since it is the same instruction a phishing page gives. It also could not work for long: nothing refreshes a pasted header, so `__Secure-1PSIDTS` retires within minutes and every stream comes back 403 while browsing goes on answering, which reads as the app breaking rather than as the session expiring. `validateCookieHeader`, the `auth:import-cookies` channel and its bridge method went with it, and the "No signed-in browser found" branch of `src/components/sign-in.tsx` is the only fallback left: it names the five supported browsers and offers to look again.
- The sign-in view is the app's disclosure, and its wording is load-bearing rather than decoration. It said "Nothing leaves this device", which is what the app promises about telemetry and is not true of the thing that screen is actually about: the cookies go to YouTube on every request, because they are the session. So it states where they go, states that the browser profile is re-read while the app runs rather than read once, and closes on the fact that carries the real risk, that Noctune reaches YouTube through the private interface the YouTube Music apps use and the linked account carries whatever that brings. There is no acknowledgement checkbox and there must not be one: it is friction nobody reads, and it would not move responsibility anywhere a sentence does not. `README.md`, `PRIVACY.md`, `SECURITY.md` and `CONTEXT.md` state the same three facts, so a change to any of them is a change to all of them.
- The app has two marks, an N monogram cut by a play triangle, and which one is on screen says which build is running: `build/icon.png` is red and is the released app, `build/icon-dev.png` is blue and is what `app.dock.setIcon` puts on a development run, beside `src/assets/logo.png` and `logo-dev.png`, the 192px copies the sign-in view picks between on `import.meta.env.DEV`. `build/icon.icns` is generated from the red one with `iconutil` and is the only one electron-builder reads. The two dock icons are drawn against Apple's grid, an 824x824 tile centred on a 1024x1024 transparent canvas rather than the full canvas, or the icon renders about a quarter larger than its neighbours in the Dock. The renderer's copies are the bare tile instead, since the sign-in badge rounds them in CSS at display size, which is sharper at 44px than a radius baked in at 192.
- Both dock marks carry a channel badge, a white pill in the tile's bottom right reading "BETA" on the red one and "DEV" on the blue one, with the label drawn in the tile's own colour sampled from the gradient beside it. It is 162px tall on the 824 tile, inset 44px from the tile's right and bottom edges. Both numbers have a ceiling: the inset cannot shrink much further before the pill's diagonal extreme crosses the 185.4 rounding, and past about 175px tall the badge takes enough off the monogram's right leg that the two legs end at visibly different heights and the mark reads as damaged. At 162 it covers the leg's last 39px, so a 14px ring of the sampled background colour is painted under the pill and clipped to the tile's alpha: white meeting white read as a foot on the glyph, and the gradient moves two or three units across that span, so a flat fill is indistinguishable from what it covers. The 192px renderer marks stay unbadged, since the sign-in view draws them at 44px, where the label is unreadable. Only the badged icons are committed and there is no generator: the unbadged masters are in git history, and `build/icon.icns` is regenerated with `iconutil` from the badged `build/icon.png`. Dropping the badge at 1.0 means restoring that master, not editing a script.
- Source artwork arrives as a full-bleed square, so neither the corners nor the glyph's size can be taken as they come. The rounding is the app's own (radius 185.4 on the 824 tile, supersampled), and the monogram is lifted off its gradient as an alpha mask, rescaled to 60% of the tile's height and pasted back onto a gradient re-synthesised bilinearly from the source's four corner colours. Both halves matter: pasting the square as it arrives draws a square in the Dock, and leaving the glyph at the 72% it is drawn at leaves no margin inside the rounding, which is what "the icon looks too big" means every time. The mask is read off whichever channels have room to move (a white glyph says nothing about coverage in a channel whose background is already near 255), which is what keeps the antialiased edges clean.
- Development runs the stock Electron binary, so macOS takes the Dock label, the Cmd-Tab entry, and the app menu title from that bundle and ignores `app.setName`. `scripts/dev-app-name.mjs` runs on `postinstall` and renames the bundle to `Noctune.app`, rewrites `node_modules/electron/path.txt` to match, and rewrites the two name keys to "Noctune (Dev)". The bundle path keeps the plain name because `path.txt` points at it. It then signs the bundle again, ad-hoc: Electron ships a linker-signed binary, editing `Info.plist` breaks that seal, and `UNUserNotificationCenter`, which is what Electron posts a notification through on macOS, refuses an app whose signature does not validate. Every notification comes back `UNErrorDomain 1` and macOS never asks for permission, since it will not register the app at all, so the feature looks unimplemented rather than refused. `codesign --verify --strict node_modules/electron/dist/Noctune.app` is what says which side of that a dev bundle is on. It runs on `dev` as well as `postinstall`, because anything that re-extracts `node_modules/electron` (an install carrying `--ignore-scripts`, an interrupted one, a prune) puts the stock `Electron.app` back, and the failure that follows is the silent one: `pnpm dev` starts normally and every notification comes back refused. An ad-hoc signature's designated requirement is a bare `cdhash`, so the grant is pinned to the exact bytes, and macOS goes on showing the row for the identity it was granted to while refusing the app that replaced it. Development also has Electron's own icon, which is why main calls `app.dock.setIcon` when `VITE_DEV_SERVER_URL` is set. That call reaches the Dock and nothing else, though: a notification's leading icon, Finder and the rest all read the bundle's own `Contents/Resources/electron.icns`, so the script writes the blue mark over it before it signs. `sips` refuses to write an icns at 1024 and is given `-Z 512`, which is larger than anything drawing it asks for and saves building an iconset for `iconutil`. Packaged builds need neither: electron-builder downloads its own Electron and names and paints it from the `build` field.
- Only development is named for its channel. `APP_NAME` in `electron/main.ts` is "Noctune (Dev)" on a development run and plain "Noctune" packaged, and it is what `app.setName` and the app menu's first label take, while the Dock label and the Cmd-Tab entry read the two plist keys `scripts/dev-app-name.mjs` writes. The released app says it is prerelease on its icon and nowhere in its name, so nothing has to be renamed back at 1.0 and `productName` stays the one word the `.app`, the DMG, the ZIP and `scripts/staple.mjs` all resolve through. `app.setPath("userData", …)` takes that same name, so the two channels never share a data path: a development run has its own linked account, downloads, playback state, settings and cookies, and both can be open at the same time, which one directory does not survive, since two Chromium processes then write the same cookie and Local Storage databases. The path is set rather than left to Electron, which derives it from the app name and would follow the bundle's rather than `productName` if the two ever differed. It is not derived from the channel anywhere else: everything under `userData` (`linked-account.json`, `downloads`, `youtube-cache`, the state file, the log, the auth partition) is already joined onto it, and Electron's own single-instance lock file would be too. What the two still share is what macOS keys to the bundle rather than the path: the stock Electron binary a development run uses is `com.github.Electron`, so its notification permission and TCC identity are the ones every other stock-Electron app on the machine holds. Changing that is one more `plutil -replace` in `scripts/dev-app-name.mjs` ahead of the re-sign, at the cost of re-granting the notification permission and the Chrome Safe Storage Keychain prompt once. A local `pnpm package` build has no `VITE_DEV_SERVER_URL`, so it reads the released app's data, which is the point of it.
- Style with Tailwind utilities and the semantic tokens. `src/styles.css` holds tokens and a handful of global rules only, not page CSS.
- The keyboard focus ring is suppressed on purpose: `*:focus-visible` in `src/styles.css` clears the outline and sets `--ring: transparent`, which is enough because every `ring-ring`, `border-ring` and `outline-ring` in the app resolves that token inline (`@theme inline`). The rule is deliberately unlayered so it wins over the utilities without `!important`. A new focus style that hard-codes a colour instead of using `--ring` escapes it. A text field is the one exception, and gets the accent back through a second unlayered rule giving `input:focus-visible` and `textarea:focus-visible` `--ring: var(--primary)`: everything else is reached by tabbing, where the reader already knows what they landed on, while a field is reached by clicking into it and with no ring at all nothing says where the next keystroke goes. Nothing in `src/components/ui/` is edited for it, since those already carry `focus-visible:border-ring` and `focus-visible:ring-ring/50`.
- A form label in a dialog names its control with `aria-labelledby` and not `htmlFor`. A label bound to a control forwards a click onto it, so pressing the word "Description" put the caret in the field and pressing "Privacy" opened the select, which is not what a heading over a field should do. The accessible name is identical either way.
- Nothing in the app is a drag source, so `img` and `a` both carry `-webkit-user-drag: none` in the base layer of `src/styles.css`. Artwork dragged out of the window lands in another app as a file, and a link dragged out lands as its URL, neither of which this app offers on purpose. Both selectors are needed: refusing the image alone hands the drag to the anchor wrapping it, which is most of the covers on Home, Explore and search.
- The shell's middle column pays for everything beside it: the navigation rail and the Now panel are `auto` tracks holding a fixed 224px and 384px, so a small window leaves the page being read with whatever is left. The rail's labels are the only part of that worth taking back, which is what `useRailLabels` in `app-shell.tsx` does below 960px, and only while the panel is open, since a small window on its own has room for both. Floating the panel over the page instead frees nothing: it is anchored to the same edge the page column ends at, so the width a reader can see is `window - rail - 384` either way and the only thing an overlay adds is content hidden underneath it. It also makes the page column measure wider than it draws, which is worse than the crowding it was meant to fix.
- Below the shell, a viewport breakpoint is the wrong instrument entirely: the rail and the panel each open and close without the window changing size at all. A page that has to respond to its own width declares a `@container` and queries that, which is what `/settings` does for its tab rail (labels go, icons stay, the name moves to `aria-label` and `title`) and for its rows (the control drops under its label rather than wringing the description out a word at a time). The two mechanisms have to agree on direction: collapsing the rail is a step up in page width, and a step up landing across one of those container breakpoints un-stacks a row or brings a label back as the window gets *smaller*. 960px is chosen so both sides of that step stay under every one of them: the column is `width - 448 - 48` once the rail is icons, the narrower breakpoint is 512, so the rail has to collapse before 1008px or the page reverses. Moving either number means redoing that arithmetic.
- Keep `id="main-scrollable-area"` on the scroll container for router scroll restoration, and keep `class="drag-region"` on the top bar (and on the sign-in view's top strip) or the frameless window stops moving.
- Never expose cookies, signed URLs, upstream parser objects, arbitrary URLs, filesystem paths, or lyric text in logs.
- Do not disable Electron sandboxing, context isolation, CSP, sender validation, or `webSecurity` to work around an upstream failure.

## Commands

- `pnpm dev`: run the Electron and Vite development app.
- `pnpm check`: formatting, lint, type checking, unit tests, route generation, and production build.
- `pnpm package`: create an ad-hoc signed local macOS app directory. Ad-hoc rather than unsigned (`-c.mac.identity=-`) because macOS refuses notifications from a bundle whose signature does not validate, and electron-builder rewrites `Info.plist`, which breaks the seal on the signature Electron ships with. It is the same trap `scripts/dev-app-name.mjs` works around.
- `pnpm release:gate`: block distribution unless technical gates and lyric-rights review are complete.
- `pnpm dist`: run release gates and build signed, notarized and stapled DMG and ZIP artifacts, publishing nothing. Four submissions to Apple, an app per architecture and a disk image per architecture, so it is minutes of waiting and worth running under `caffeinate -is`.
- `pnpm release:patch`, `pnpm release:minor`, `pnpm release:major`: run `pnpm check`, bump the version, commit it as `chore(release): v<version>` and tag it, stopping there. `git push --follow-tags` is a separate command on purpose. The tag is the whole release trigger, everything after it happens in Actions.
- `pnpm release:notes`: print the notes the tag would publish, from the commits behind it. Read it between tagging and pushing, since that is the last point anything can still be changed.
- `pnpm release:retag`: move the current version's tag onto `HEAD`, for a fix committed after the bump. It reads the version out of `package.json` rather than taking one, since a mistyped version silently creates a second tag instead of moving the one that exists, and it repeats the `chore(release): v<version>` message `pnpm version` wrote, since `tag.gpgsign` makes every tag annotated and an annotated tag with no message is refused outright. Only ever run it on a tag that has not been pushed.
- `pnpm release:push`: `git push --follow-tags`, the command that actually releases. It is a script rather than a bare git invocation so the whole sequence reads as one group, and so the tag is never left behind by a plain `git push`.

## Signing and notarization (macOS)

- `docs/signing.md` is the step by step guide, from creating the certificate to the GitHub secrets. The rules it follows are below.
- Nothing names the certificate. electron-builder finds the one `Developer ID Application` identity in the login keychain by itself, and `CSC_LINK`/`CSC_KEY_PASSWORD` in `.github/workflows/release.yml` are how the same identity reaches a machine with no keychain to find it in. There is no `mac.identity` and no entitlements file: the default entitlements electron-builder writes under `hardenedRuntime` are the three Electron needs.
- Credentials go in `electron-builder.env` (gitignored, `electron-builder.env.example` is the template), which electron-builder's own CLI reads from the project root and never packs into the app. A variable already set in the shell wins over the file.
- `mac.notarize` is `false` in the config and `pnpm dist` turns it on with `-c.mac.notarize=true`, which is the one direction that works: the CLI coerces only `mac.identity` to a boolean, so a `false` passed as a flag arrives as a truthy string, while the skip test is a strict `=== false`. Off by default is also what keeps the ad-hoc `pnpm package` from submitting a build Apple will reject, now that the credentials are in a file every electron-builder run reads. `dmg.sign` needs no such switch: `pnpm package` passes `--dir`, so it builds no image for it to sign.
- electron-builder notarizes from `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_APP_SPECIFIC_PASSWORD` on its own, so nothing calls `@electron/notarize` here. `scripts/staple.mjs` is the `afterSign` hook and does the one thing electron-builder does not: attach the ticket, before the DMG and ZIP are built around the app. Without it a downloaded build has to reach Apple the first time it is opened.
- The disk image is signed, notarized and stapled in its own right, and none of that can happen in `afterSign`, which runs before the image exists at all: `mac.notarize` submits the app alone, so a release whose app passed every check still handed a reader an image Gatekeeper refused before the app inside it was ever reached. `dmg.sign` is the first half and is electron-builder's own, signing each image as it is built with the identity and the `--keychain` it already found for the app, which is why nothing here names a certificate either. `scripts/finish-dmgs.mjs` is the second half. The app's submission stays beside it rather than being replaced by the image's: the ZIPs the updater installs are built around the bundle, and a ticket stapled to the image reaches nothing inside it.
- Both images are submitted at once (`Promise.all`), since a submission is minutes of waiting on a server and the release already spends two of them on the apps, one per architecture. `stapler` is what makes a rejection loud: it refuses a submission Apple marked `Invalid`, so it is the gate rather than `notarytool`'s exit code. The hook reads the three credentials straight off `process.env`, which electron-builder's CLI has already loaded `electron-builder.env` into by the time any hook runs.
- `pnpm release:gate` runs as a process of its own and reads the same file through `--env-file-if-exists`, since the CLI's copy of it never reaches a separate node.

## Releasing and updating

### Cutting a release

"Release a new patch version" (or minor, or major) means exactly this, in order. Steps 1 to 5 are local and cost nothing to redo. Step 6 is the one that cannot be taken back, so stop there and ask, every time, even when the rest went perfectly.

1. Be on `main`, in sync with `origin/main`, with a clean tree. `pnpm version` refuses a dirty one, and anything uncommitted is simply not in the release. Commit or say what is outstanding first.
2. `pnpm release:patch`, `pnpm release:minor` or `pnpm release:major`, whichever was asked for. It runs `pnpm check`, bumps `package.json`, writes and signs the `chore(release): v<version>` commit and its tag, and stops. A failed check leaves nothing behind at all, which is the point: fix and run it again rather than unpicking a half-made release.
3. `pnpm release:notes`. Read what the tag would publish and show it. The notes are the commit subjects, so a wrong line is a wrong commit message: amend it, then `pnpm release:retag`.
4. `git diff v<version> HEAD --stat`. Empty output means the tag builds what is actually in front of you. Anything else means the tag is behind a later commit, which `pnpm release:retag` fixes.
5. Report the version, the notes and the diff result.
6. `pnpm release:push`, only on an explicit go-ahead. The tag arriving on the remote starts the workflow, and from that moment the version is a fact: a published release may already have been served to an installed copy through `latest-mac.yml`, so a bad one is fixed by the next version and never by reusing this one.
7. `gh run watch`. When it lands, count what was published before trusting the green tick, since the run reports the upload it made and not the release a reader ends up on: `gh api "repos/NoctunePlayer/NoctuneDesktop/releases?per_page=20"` lists drafts too, and the tag must name exactly one release, holding the seven files described below and nothing else. A second release under the same tag, or a published one missing the DMGs, is the split draft described below. Then verify the published artifact rather than the local build: download the Apple Silicon DMG, which carries `com.apple.quarantine` the way a reader's copy does, and check the image itself before what is inside it, since that is the order Gatekeeper takes them in. `spctl -a -vvv -t open --context context:primary-signature <dmg>` must report `accepted` with `source=Notarized Developer ID`, and `xcrun stapler validate <dmg>` must pass. Then mount it and run `spctl -a -vvv -t exec` and `xcrun stapler validate` against the app inside.

- A release is two commands and one tag. `pnpm release:patch` (or `:minor`, `:major`) runs `preversion`, which is `pnpm check`, bumps `package.json`, writes the `chore(release): v<version>` commit and tags it, and then stops. `git push --follow-tags` is what releases. Nothing is built locally: the tag matching `v[0-9]+.[0-9]+.[0-9]+` is what starts `.github/workflows/release.yml`, and a failed check means the tag was never written rather than a release that has to be deleted. There is no `postversion` on purpose: pushing from inside the bump left no point at which the notes could be read or a mistake in them fixed, since everything downstream of the tag is decided by commits that are by then already public. A tag that has not been pushed is still local, so it can be moved (`git tag -d`, amend, tag again) at no cost.
- That workflow builds both architectures in one electron-builder run. Two jobs each publishing their own `latest-mac.yml` would leave whichever finished last as the update feed every installed copy reads, and the other architecture would then be offered a build it cannot run. One run writes one feed naming both.
- The release is created as a draft (`build.publish.releaseType`), which is what makes the ordering work rather than being a nicety: electron-updater cannot see a draft, so every artifact is attached and the notes are written onto it before `gh release edit --draft=false` publishes it in a single move. Nothing ever sees a release with no notes or half its files. The workflow creates that draft itself, in a `gh release create --draft` step of its own, and the build then runs `--publish never` and a `gh release upload` step attaches the directory afterwards. electron-builder must not do the publishing: it runs a publisher per architecture and starts both before either has created anything, and a draft is not keyed to its tag, so GitHub refuses neither. v0.1.1 produced two drafts for one tag, split its nine artifacts eight to one between them, and `gh release edit` published the one holding a single blockmap while both DMGs stayed in the draft nobody could see. Uploading after the build is also what lets the artifacts be renamed at all, since a publisher uploads each file as it lands, which is before any hook that runs when the build is done. `latest-mac.yml` is written either way: it is generated from the artifacts (`createUpdateInfoTasks`, outside the `isPublish` branch) rather than from the upload.
- A release is seven files, and every one of them is read by something. `latest-mac.yml` is the feed and the only thing the updater fetches by name. The two ZIPs are what it installs: macOS updates through Squirrel.Mac, which can only swap in a zipped `.app`, and `MacUpdater` picks the file with `findFile(files, "zip", ["pkg", "dmg"])`, which excludes the DMG by name and throws `ERR_UPDATER_ZIP_FILE_NOT_FOUND` when there is no ZIP. Their two `.blockmap` files are what keep an update from being another 130 MB: the updater fetches the old and the new blockmap, diffs the chunk hashes, and downloads only the ranges that changed, falling back to the whole file with a line in the log when either is missing. The two DMGs are for a reader, and are the two files that reach nothing else, which is why `dmg.writeUpdateInfo` is `false`: it stops the DMG blockmaps nothing has ever fetched, and takes the DMGs out of the feed they were listed in and never read from.
- Which is also why only the DMGs are named for the Mac they are for. `scripts/finish-dmgs.mjs` renames them on `afterAllArtifactBuild`, which is also the only hook holding both finished images and so the one that notarizes and staples them. The rename runs first, so the file Apple mints a ticket for is the file that ships: a signature and a ticket both live inside the image rather than being keyed to its path, so either order works, and this one leaves no step handing the next a path that later changes. The rename is there at all because electron-builder has no per-architecture `artifactName` (the template's only lever is `${arch}`, the raw `x64` or `arm64`) and left to itself it names the Intel build `Noctune-<version>.dmg`, with the architecture that says nothing being the one a reader is least likely to want. The ZIPs keep their generated names and must keep them: `latest-mac.yml` states no architecture anywhere, so `MacUpdater.filterFilesForArch` decides what an Apple Silicon Mac gets by testing each file's url for the substring `arm64`. A ZIP renamed to say "applesilicon" matches nothing there, and every Apple Silicon install would quietly take the Intel build and go on running it under Rosetta. Nothing in the app reads any of these names.
- Those notes are generated by `git-cliff` from the Conventional Commits behind the tag, through `pnpm dlx` rather than a dependency or a third-party action, so the same command previews them locally, which is what `pnpm release:notes` is. Keep the version it pins in step with the one the workflow runs, since a preview from another version is not the thing being published. There is nothing to hand-edit before a release: the notes are the commit subjects, so a wrong line is a wrong commit message and is fixed by amending it while the tag is still local. Wording that only matters on the release page is edited afterwards with `gh release edit --notes-file`, which changes the page and leaves the history alone. `cliff.toml` holds the ordering trick: `group_by` sorts headings alphabetically, so each group name carries an HTML comment (`<!-- 1 -->Features`) that orders them and renders as nothing. It skips the release commit itself, drops anything that is not a Conventional Commit, and reads only `v` tags, since `pre-noctune-history` is a marker and `--latest` would otherwise measure a range from it. A release-notes tool that also decides the version (release-please, semantic-release) is the wrong shape here: the version is chosen by hand, by the person running the command.
- `pnpm package` and `pnpm dist` both pass `--publish never`. electron-builder publishes on its own once a `publish` block exists and it believes it is on a tag, and a local build is never what should reach the releases page.
- The updater lives in `electron/main.ts`. It checks at startup and every six hours after it, since a music player is left running for days and a check made once at launch is one most installs never make twice. `autoDownload` is on, which leaves the restart as the only thing ever asked of the listener, and it is also what makes "later" free rather than a deferral: `autoInstallOnAppQuit` is electron-updater's own default, so a build downloaded and left alone installs itself the next time Noctune is quit, with no second prompt and no second download. That is why there is no `update:download` channel: nothing can reach it. `autoUpdater.logger` is `null` because electron-updater's own logger writes the feed URL and the cache path it downloads into, which is a filesystem path in a log this app promises not to write. Its failures go through `LocalLogger` as one line naming the reason.
- Main owns `UpdateState` and pushes every change over `update:state`, since the check runs at startup and the About tab is opened minutes later: a renderer that only listened would show nothing at all until something changed. `src/lib/updates.ts` is the renderer's half, a store for the same reason the library and the ratings are: it reads the state once and follows the pushes, and three things read it. Its `checkForUpdates` is optimistic for the same reason a rating is, and it is why every button that checks goes through it rather than calling the bridge: the round trip out to main and back is long enough to press the button a second time in, and it is drawn enabled for all of it, so the state it is about to be put in is written on the press. The answer is then held to a floor of half a second, which is the other half of the same problem: a check that comes back faster than it can be read changes the button and changes it back inside a frame or two, which reads as a glitch rather than as the one answer with nothing else to show for itself. Only the answer is held and only once, since a download's percent and its arrival are their own events at their own pace. The rail badges its Settings entry while a build is `ready`, and it is also what starts the subscription, since it outlives every page. The About row describes the whole lifecycle, where `available` is drawn as `downloading` rather than as a state of its own, since with `autoDownload` on nothing rests there. And the toast is the prompt, announced once on the arrival at `ready` rather than on every push, since a download ticking its percent would otherwise replace it under the pointer. That toast has no timeout: the download has already happened, so the only question is the restart, and a listener who left the room to a full album should not come back to a decision that timed out. Dismissing it is the "later", and the rail dot is what is left of it. Every state draws a row, including the `unsupported` one the store starts on: an updater that only appears once it has something to say is one nobody can ask, and "nothing to install" is worth as much as the offer to install something. A development build stays in that state, since `app.isPackaged` is false, there is no feed to ask and no signature for macOS to accept, so its button answers nothing and it never badges the rail.
- `electron-updater` is imported as a default export and destructured (`const { autoUpdater } = electronUpdater`). It is CommonJS, and a named import of it from an ES module resolves to nothing at runtime. It is a real dependency rather than a dev one, and like `youtubei.js` it is bundled into `dist-electron/main/index.js`, which is why `build.files` names no `node_modules`.
